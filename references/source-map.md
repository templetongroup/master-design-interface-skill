# Source map

This file records how the installed design library was synthesized. The master skill preserves the source skills and resolves their overlap; it does not concatenate or replace them.

## Orchestration and review

- `general-design-review`: compact product, UX, AI, craft, research, and prioritization routing.
- `better-interface`, `better-accessibility`, `better-layout`, `better-writing`, `better-typography`, `better-colors`, `better-ui`: domain ownership, evidence requirements, systemic consolidation, severity, coverage, and verdict.
- `interface-review`: change-scope resolution, diff classification, consumer expansion, and non-mutating review.
- `design-review`, `impeccable-design-polish`: launch polish, before/after evidence, restraint, and hardening.
- `accessibility`: WCAG-oriented visual and code checks.
- `code-review`: exact evidence and regression discipline when design work overlaps source changes.

## Product and research

- `double-diamond`, `ux-research-methods`: discover/define/develop/deliver and method selection.
- `ux-personas`, `empathy-mapping`, `journey-mapping`, `ux-storyboard`: evidence-grounded actors, behavior, context, emotion, and sequence.
- `ux-heuristics-review`, `cognitive-load-conversion`: clarity, control, recognition, recovery, and avoidable mental effort.
- `persuasive-ux`: ethical reduction, tunneling, timely suggestion, self-monitoring, and reinforcement.
- `feature-prioritization`: value, reach, risk, feasibility, and effort tradeoffs.
- `dieter-rams-principles`: usefulness, honesty, restraint, thoroughness, and longevity.

## AI experience

- `ai-inputs`: task-appropriate input and transformation patterns.
- `ai-wayfinders`: examples, suggestions, templates, and contextual starts.
- `ai-trust-builders`: scope, evidence, confidence, provenance, and user control.
- `ai-governors`: confirmation, preview, interruption, undo, and consequential-action boundaries.
- `ai-tuners`: steering, comparison, regeneration, and recoverable refinement.
- `ai-identifiers`: honest AI presence and output attribution.

## Visual direction and anti-slop

- `craft`: token-level spacing, typography, neutral, elevation, state, and motion discipline.
- `redesign-existing-projects`: targeted upgrades in the existing stack rather than cosmetic rewrites.
- `design-analysis`: measured extraction of typography, color, layout, imagery, space, depth, motion, and voice.
- `hallmark`, `design-taste-frontend`, `design-taste-frontend-v1`, `gpt-taste`, `high-end-visual-design`: strong creative direction, anti-template judgment, system memory, and distinctiveness.
- `minimalist-ui`, `industrial-brutalist-ui`: style-specific routes retained as conditional aesthetics, never universal mandates.
- `stitch-design-taste`, `ui-skills`, `ui-ux-pro-max`: semantic tokens, interface constraints, and component consistency.
- `brandkit`: approved brand assets and roles as design-system inputs.
- `emil-design-eng`: implementation-level interaction and visual detail.

## Platform, reconstruction, and production

- `apple-hig`, `swiftui-design`, and `build-macos-apps:*`: native conventions, window behavior, SwiftUI/AppKit implementation, build, signing, packaging, and release mechanics.
- `image-to-code`, `imagegen-frontend-web`, `imagegen-frontend-mobile`: reference interpretation, visual assets, and reconstruction workflows.
- `prototype`: fast disposable validation before committing to a direction.
- `better-interface` plus repeated native release audits: installed/deployed evidence, surface-by-state verification, and release truth.

## Conflict decisions

- Treat gradients, pure black/white, symmetry, cards, serif type, texture, and motion as contextual—not blanket bans.
- Prefer platform-native behavior over a custom visual replica.
- Prefer an accepted target or brand system over automatic diversification.
- Prefer one coherent project system over forcing every screen to look different.
- Prefer accessibility and truthful product state over visual minimalism.
- Prefer measured rendered evidence over taste claims.
- Prefer shared-root fixes over one-screen patches.
- Prefer real installed/deployed interaction over source-only completion claims.

When updating this master skill, incorporate new durable principles into the appropriate reference. Do not copy an entire source skill unless its procedure must remain independently executable.
